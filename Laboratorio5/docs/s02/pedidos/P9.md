# P9 — Sincronização com serviço externo instável

**Tipo:** Tensiona a arquitetura
**Ordem na coleta completa:** definida no protocolo congelado

---

[CONTEXTO] O projeto está no diretório atual.

[NECESSIDADE] Tarefas concluídas devem ser notificadas a um serviço externo de registro de
atividades. Esse serviço é instável: pode estar fora do ar ou responder com erro. O sistema
não pode deixar de funcionar por causa da instabilidade do serviço externo.

[COMPORTAMENTO PARA O USUÁRIO] Ao concluir uma tarefa, o sistema tenta notificar o serviço
externo em `POST /notificacoes` (stub). Se o serviço retornar erro ou não responder em até
500ms, o sistema registra a falha internamente e continua. O usuário recebe a confirmação de
que a tarefa foi concluída normalmente, independente do resultado da notificação.

A tela mostra o status da notificação na área `data-testid="status-notificacao"`: `enviada`,
`falhou` ou `pendente`. Reenvio manual pode ser feito pelo botão
`data-testid="reenviar-notificacao"`.

**Contrato do stub (determinístico):** a URL do stub é configurada por variável de ambiente
`NOTIFICACAO_URL`. O stub responde com 200 nas requisições de número par (1ª, 3ª, 5ª...)
e com 503 nas ímpares (2ª, 4ª, 6ª...), contando por instância do stub. Isso garante
determinismo nos testes sem depender de aleatoriedade.

[CRITÉRIOS DE ACEITAÇÃO]
- Concluir uma tarefa quando o stub retorna 200 resulta em status `enviada` na área
  `data-testid="status-notificacao"`.
- Concluir uma tarefa quando o stub retorna 503 resulta em status `falhou`, e a tarefa é
  marcada como concluída normalmente.
- Concluir uma tarefa quando o stub não responde em 500ms resulta em status `pendente` ou
  `falhou`, e a tarefa é marcada como concluída normalmente.
- O botão `data-testid="reenviar-notificacao"` tenta novamente a notificação de uma tarefa
  com status `falhou`.

[SAÍDA] Implemente a mudança no próprio projeto. O resultado será verificado por testes
automatizados de comportamento.

## Mínimo observável

| Elemento | Identificador |
|---|---|
| Área de status de notificação | `data-testid="status-notificacao"` |
| Botão de reenvio manual | `data-testid="reenviar-notificacao"` |
| Variável de ambiente do stub | `NOTIFICACAO_URL` |
| Endpoint do stub | `POST /notificacoes` |

## Contrato do stub (para escrita dos testes)

| Requisição nº (por instância) | Resposta do stub |
|---|---|
| Par (2ª, 4ª, 6ª...) | 200 OK |
| Ímpar (1ª, 3ª, 5ª...) | 503 Service Unavailable |

> O stub deve ser implementado pelos testes como servidor HTTP leve. O comportamento ímpar/par
> é a regra determinística definida antes da coleta para garantir reprodutibilidade.

## Rastreio critério ↔ teste (caixa-preta)

| Critério | Caso de teste sugerido |
|---|---|
| Stub 200 → status `enviada` | `notificacaoEnviadaComSucesso` |
| Stub 503 → tarefa concluída, status `falhou` | `notificacaoFalhoNaoImpedeConclussao` |
| Timeout 500ms → tarefa concluída | `timeoutNaoImpedeConclussao` |
| Botão reenviar tenta notificação novamente | `reenvioManualFunciona` |
